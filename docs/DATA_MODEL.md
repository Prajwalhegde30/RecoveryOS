# RecoveryOS Data Model

**Status:** Proposed baseline — architecture review pending

## 1. Modeling principles

- One recoverable business obligation equals one Recovery Case.
- Payment attempts, events, actions, jobs, incidents, and messages are supporting records; none independently create revenue totals.
- PostgreSQL is the financial/workflow source of truth.
- IDs are opaque UUID/ULID-style identifiers generated by the application; external provider IDs are retained separately.
- Monetary values are non-negative integers in smallest currency units with an ISO currency code.
- All tenant-owned records carry `merchant_id` directly or through a constrained parent relationship.
- State changes, policy decisions, actions, and financial reconciliation are auditable.
- Schema changes use versioned migrations; application startup does not mutate schema.

## 3. Core tables and fields

The following are logical tables. Exact SQL types, naming, timestamps, indexes, and migration details are finalized in implementation while preserving these invariants.

### merchants

`id` PK, `external_key` unique, `name`, `default_currency`, `timezone`, `environment_mode`, `created_at`, `updated_at`, `status`.

`external_key` is unique. Currency and timezone are validated. Merchant mode distinguishes demo, test, and production-like environments.

### users

`id` PK, `subject` unique within auth issuer, `email_or_label`, `created_at`, `status`.

### merchant_memberships

`merchant_id` FK, `user_id` FK, `role` enum (`VIEWER`, `OPERATOR`, `ADMIN`), `created_at`, `updated_at`.

PK is `(merchant_id, user_id)`; role changes are audited. A user may belong to multiple merchants but every request resolves one active merchant scope.

### customers

`id` PK, `merchant_id` FK, `external_customer_id`, minimal `name`, `email`, `phone`, `status`, `opted_out_at`, `created_at`, `updated_at`.

Unique `(merchant_id, external_customer_id)`. Sensitive fields are minimized and access-controlled. Customer contact data is never used as an identity key for financial obligations.

### obligations

Represents the normalized payable business obligation behind a case. Fields: `id` PK, `merchant_id` FK, `obligation_type`, `external_obligation_id`, optional `order_id`, `checkout_intent_id`, `subscription_id`, `billing_cycle_id`, `invoice_id`, `amount_at_risk`, `currency`, `status`, `authoritative_status`, `due_at`, `paid_at`, `created_at`, `updated_at`.

Logical uniqueness is `(merchant_id, obligation_type, external_obligation_id)`. The exact obligation identity rules are source-specific and documented in the PRD.

### recovery_cases

Fields: `id` PK, `merchant_id` FK, `customer_id` FK nullable, `obligation_id` FK unique, `source_type`, `status`, `root_cause`, `root_cause_confidence`, `recovery_probability`, `probability_version`, `expected_recoverable_amount`, `priority_score`, `priority_version`, `attempt_count`, `max_attempts_snapshot`, `recovered_amount`, `currency`, `attribution_status`, `incident_suppressed`, `opened_at`, `closed_at`, `created_at`, `updated_at`.

One obligation maps to at most one case. `obligation_id` is unique. `recovered_amount` is updated only from authoritative reconciliation or an auditable correction. Case status changes use an application transition service.

### payment_attempts

Fields: `id` PK, `merchant_id` FK, `recovery_case_id` FK, `external_payment_id`, `payment_method`, `provider`, `amount`, `currency`, `status`, `failure_code`, `provider_event_at`, `created_at`, `updated_at`.

Unique `(merchant_id, provider, external_payment_id)`. Multiple attempts may point to one case. A successful attempt does not create a second case or second recovery total.

### revenue_events

Fields: `id` PK, `merchant_id` FK, `provider`, `external_event_id`, `event_type`, `source_object_id`, optional `obligation_id`, optional `recovery_case_id`, normalized payload, `provider_event_at`, `received_at`, `processed_at`, `processing_status`, `correlation_id`.

Unique `(merchant_id, provider, external_event_id)`. Raw payload retention is minimized and access-controlled; normalized facts are preferred.

### processed_events

Fields: `id` PK, `merchant_id` FK, `provider`, `idempotency_key` unique within provider/merchant, `event_type`, `first_seen_at`, `result`, `correlation_id`.

This table supports safe duplicate webhook handling. A duplicate returns the prior processing result and cannot create another case, attempt, action, or financial effect.

### recommendations

Fields: `id` PK, `merchant_id` FK, `recovery_case_id` FK, `source` (`AI`, `DETERMINISTIC_FALLBACK`, `RULE`), `action_type`, `parameters_json` schema-validated, `reason_code`, `rationale`, `evidence_json`, `confidence`, `prompt_version` nullable, `model_version` nullable, `scoring_version`, `created_at`.

Recommendations are proposals. They do not authorize action, establish payment status, or update financial amounts.

### merchant_policies and policy_versions

`merchant_policies`: `id` PK, `merchant_id` FK unique, `current_version_id`, `updated_at`.  
`policy_versions`: `id` PK, `merchant_id` FK, `version`, typed policy JSON, `created_by`, `created_at`, `status`.

Policy JSON is validated against a versioned schema. Every decision/action/job stores the policy version used. Historical versions are retained for audit and reconstruction.

### policy_decisions

Fields: `id` PK, `merchant_id` FK, `recovery_case_id` FK, optional `recommendation_id`, `policy_version_id` FK, `result`, `decisive_rule`, `reason`, `input_snapshot_json`, `created_at`, `actor_type`, `correlation_id`.

Decisions are append-only. A later re-evaluation creates a new decision rather than overwriting history.

### recovery_actions

Fields: `id` PK, `merchant_id` FK, `recovery_case_id` FK, optional `recommendation_id`, `action_type`, `channel`, `status`, `idempotency_key` unique within merchant, `attempt_number`, `provider_reference`, `cost_minor_units`, `requested_at`, `executed_at`, `cancelled_at`, `failure_category`, `failure_detail_safe`, `correlation_id`.

The idempotency key prevents duplicate outbound effects. Action status is distinct from case status.

### scheduled_jobs

Fields: `id` PK, `merchant_id` FK, optional `recovery_case_id` FK, optional `recovery_action_id` FK, `job_type`, `status`, `due_at`, `attempt_count`, `max_attempts`, `lease_until`, `next_retry_at`, `idempotency_key` unique within merchant, `last_error_category`, `last_error_safe`, `created_at`, `updated_at`, `correlation_id`.

Jobs are durable, claimable, cancellable, and replayable only through idempotent application paths. Expired leases are recoverable after worker restart.

### incidents and case_incidents

`incidents`: `id` PK, `merchant_id` FK, `dimension_key`, `status`, `baseline_window`, `current_window`, `opened_at`, `resolved_at`, `cooldown_until`, `confidence`, `evidence_json`, `detector_version`.  
`case_incidents`: `incident_id` FK, `recovery_case_id` FK, `association_reason`, `created_at`; PK `(incident_id, recovery_case_id)`.

An incident is not an obligation and cannot be included in revenue-at-risk or recovered totals.

### experiments and assignments

`experiments`: `id` PK, `merchant_id` FK, `name`, `status`, `control_ratio`, `treatment_ratio`, `attribution_window`, `eligibility_json`, `created_at`, `updated_at`.  
`experiment_assignments`: `id` PK, `experiment_id` FK, `recovery_case_id` FK, `variant`, `assigned_at`, `assignment_version`; unique `(experiment_id, recovery_case_id)`.

Assignment occurs before treatment and is immutable for the experiment.

### attribution_records

Fields: `id` PK, `merchant_id` FK, `recovery_case_id` FK unique, `experiment_assignment_id` nullable, `outcome`, `qualifying_action_id` nullable, `attribution_window_start`, `attribution_window_end`, `verified_payment_id` nullable, `recovered_amount`, `adjustment_amount`, `confidence`, `limitations`, `created_at`, `updated_at`.

One case has one current attribution record, with adjustments represented explicitly for refunds/reversals. Duplicate success events do not create another record.

### audit_events

Fields: `id` PK, `merchant_id` FK, `entity_type`, `entity_id`, `event_type`, `actor_type`, `actor_id` nullable, `from_state` nullable, `to_state` nullable, `reason`, `metadata_safe_json`, `correlation_id`, `created_at`.

Audit events are append-only to application roles. Metadata is redacted and size-limited. State transitions, policy decisions, actions, approvals, configuration changes, simulator runs, reconciliations, and failures are auditable.

## 4. Key constraints and indexes

Required uniqueness:

- merchant/provider/external event identity;
- merchant/provider/external payment identity;
- merchant/obligation identity;
- one Recovery Case per obligation;
- one experiment assignment per case/experiment;
- one attribution record per case;
- merchant-scoped action idempotency key;
- merchant-scoped scheduled-job idempotency key.

Required indexes include merchant + status, merchant + priority, merchant + created time, merchant + due time, open cases by obligation/customer, unprocessed events, due jobs by status/due time, active incidents by dimension/status, audit entity/time, and experiment assignments by experiment/variant.

Foreign keys must prevent orphaned attempts, decisions, actions, jobs, incidents, attribution, and audit references. Delete behavior must preserve financial/audit history; use status/retention workflows rather than cascading deletion of material records.

## 5. Duplicate and race-condition prevention

### Duplicate Recovery Cases

Obligation identity and a unique `recovery_cases.obligation_id` ensure that concurrent failed events converge on one case. Event handlers must handle uniqueness conflicts by reloading the existing case.

### Duplicate payment effects

Provider payment identity and authoritative reconciliation determine whether a payment is new, duplicate, reversed, or already associated. Amounts are not incremented merely because an event repeats.

### Duplicate action execution

The application reserves an action idempotency key before provider execution. Retries query the recorded action/provider reference and return the prior result instead of sending another message or creating another link.

### Duplicate recovered revenue

Recovered revenue is tied to one obligation and one verified payment identity. Attribution and reporting aggregate the reconciled case amount once, then apply explicit refund/reversal adjustments. Incident totals, message delivery, clicks, recommendations, and duplicate webhooks are never revenue sources.

## 6. Migration strategy

1. Create a baseline migration for merchant, identity, obligation, event, case, attempt, policy, action, job, incident, experiment, attribution, and audit tables.
2. Add foreign keys, check constraints, unique constraints, and operational indexes in the same or dependent migrations.
3. Run migrations explicitly in local/test/deployment workflows; do not run schema creation from application startup.
4. Use additive changes first; backfill data with idempotent scripts when required.
5. Validate constraints and reconciliation queries before removing or renaming fields.
6. Preserve old policy/scoring versions needed to explain historical decisions.

## 7. Data retention and privacy baseline

Retention periods are configuration/deployment decisions and remain `OPEN` until security architecture approval. The implementation must minimize PII, redact logs, protect customer fields by role, encrypt managed storage/in-transit data, and provide an auditable archival/deletion process that does not silently destroy financial or audit evidence.
